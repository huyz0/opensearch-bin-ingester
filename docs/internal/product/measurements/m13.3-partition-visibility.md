# M13.3 `PartitionVisibilityIT` as a distribution, on M9's rig

Status: measured on 2026-09-30 on M9's rig, the one recorded in
`m11.23-partition-visibility.md`: i5-13600KF, Windows 11 build 26200, Docker
Desktop on WSL2. RustFS is pinned by digest `8cc98017...` at the committed
`mem_limit: 1g` (M12.24). The IT's 2,500 ms bound is unchanged.

It closes M12's harvest R2 (M13 criterion 3).

## What each run records

The IT now prints one line per inbox size:

```
M13.3 inbox= writes= trigger202= drainEnd= remaining= triggerDeferred= intentsAtTrigger=
```

- `trigger202`: from the heal to the trigger write's `202`.
- `drainEnd`: from the heal to an empty inbox. This is the number the bound
  checks.
- `triggerDeferred`: `yes` when an intent of the trigger's pod newer than
  every intent written during the partition is in the inbox right after the
  `202`. That intent is the trigger write itself, deferred instead of
  forwarded.
- `intentsAtTrigger`: the inbox's size at that moment.

⚠️ **No `trigger202 <= drainEnd` assertion**, although criterion 3 asked for
one; the criterion is corrected. Both clocks start at the heal, and `drainEnd`
is read after the trigger's `202`, so the assertion could not fail. And if the
inbox were polled concurrently, an M=10 inbox would empty before its forwarded
trigger's `202`, so the relation is not a property of the system either.

⚠️ **The instrumentation adds one LIST of the inbox inside the measured window**
(`intentsAtTrigger`), while the drain runs. `drainEnd` here is therefore not
strictly comparable with M11.23's and M12.24's.

The run script (in the session scratchpad, not committed) also reads
`docker stats` for RustFS before and after each run. For batches 2 and 3 it
also kept each run's JUnit XML. Batch 1's failures are read from the printed
`drainEnd` against the bound, because each run overwrote the previous XML.

## Findings

### The RustFS memory plateau

- **RustFS settles near the limit within a few runs of a fresh container.**
  - Batch 2 climbed 181 -> 608 -> 727 -> 810 -> 892 -> 946 MiB and settled at
    918-946 MiB, 90-92% of 1 GiB.
  - Batch 3 reached 957-1,006 MiB, 93-98%, by its second run.
  - The day-old container held at 1,013-1,018 MiB, 99%.
- **The same shape as M11.23's 256m (94%).** Raising the limit moved the
  plateau with it. M12.24's "green 3 of 3 at 1g" was measured on a fresh
  container.

### The drain overrun: the variable is not settled

- **Not reliably green as committed, and the bound is not moved.**
- **The data splits by container more than by memory.**
  - The day-old container was green 2 of 10, and its first two runs overran
    at 802 and 843 MiB.
  - The fresh containers were green 5 of 6 each, including runs at 897-990 MiB.
  - Variant B was green 3 of 4 at ~1,000 MiB.
  So memory alone does not explain the overruns. Nor does
  `CommitChargingBinStore`: variant B has the same shape as the committed code
  on a fresh container.
- **Container age or state is a candidate, not a finding.**
  - M11.23 found the opposite at 256m: a fresh container's first run was the
    worst.
  - The batches ran strictly in order, on a rig M12.24 recorded as not idle,
    so batch order and host load are confounded with container age here.
- **The inbox one second in does not tell a slow drain from a fast one.**
  - Most overruns still held all 1,001 intents at the trigger's `202`.
    Committed run 2 overran with 900.
  - Committed run 3 passed with 928, and variant B's runs 2 and 3 passed with
    1,001 and 993.
  - So "an overrun still holds all 1,001" fails in two runs either way:
    committed run 2 overran below it, and variant B's run 2 passed at it.
  - Since a drain deletes once, after every apply (`InboxDrain.drainLocked`),
    run 2's 900 means its apply had finished and its tail was in the delete.
  So these runs do not place the slow tail in one phase.
- **OBSERVED-NOT here: the cause.** It was opened as M13.45, which named it
  (below, *M13.45*): the harness replayed abandoned drains at the heal.

### The ~1.03 s trigger write: named on the follower's side

- **At M=1,000 the trigger write is deferred in every run (21 of 21; committed
  run 6 stopped at M=10), 20 of them after the 1 s timeout below.** Its `202`
  is the deferral's ack.
  - This rests on the printed `triggerDeferred` field, which no assertion
    checks.
  - The field would also print `yes` if its `>` were `>=`, since every
    M=1,000 run still held the pod's partition intents at the trigger.
- **The follower's side, against the code.**
  1. The follower is still deferring from the partition, so before forwarding
     it asks the leaseholder to drain: `FleetSequencer.commitAll` ->
     `RemoteSequencer.drain` -> `HttpSequencerTransport.drain`.
  2. That request's read timeout is the lease TTL
     (`IngesterNode.peerCommitTimeout`), 1 s in this IT.
  3. The leaseholder drains synchronously inside the request
     (`CommitService.drain`).
  4. When the drain takes longer than 1 s, the follower times out, writes the
     trigger as one more intent (`defer`, `Inbox.write`), and answers `202`.
  So ~1.03 s is that timeout, not drain work.
- **It can fail fast too.** Variant B's run 2 deferred at 77 ms, so the drain
  call failed before its timeout. M11.23's single 70 ms outlier may be the
  same, but that run had no deferral detection, so this is an inference.
- **The leaseholder's side is OBSERVED-NOT.** A drain LISTs the inbox once.
  The trigger's intent is written about a second after the heal in 20 runs,
  after that LIST (variant B's run 2, deferred at 77 ms, may not be), yet the inbox was empty at the end of all 21 M=1,000 runs. Some later
  drain applied it, and these runs do not show which. `drainEnd` includes it.
  M13.45 named it: a replayed stale drain, by luck (below).
- **At M=10 the drain beats the timeout.** The inbox was already empty at the
  trigger's `202` (0 intents), so the trigger was forwarded after the drain.
  The 8-26 ms between `trigger202` and `drainEnd` is the IT's own LISTs, not
  the drain. The field reads `not-seen` rather than `no`: an intent drained
  before the LIST would not be seen.

## Conclusion

- **Measured:**
  - 22 runs, `trigger202` and `drainEnd` recorded per run, with what each
    includes;
  - the plateau;
  - variant B, which is not the cause;
  - the trigger's cause, on the follower's side.
- **OBSERVED-NOT here:** what applies the trigger's own deferred intent, and
  the drain overrun's cause beyond "not memory alone and not the commit
  charge". Both were named by M13.45, below.
- **Not reliably green** as committed. The 2,500 ms bound is not moved.
- **Criterion 3's assertion is corrected, not added:** it could not fail.

## M13.45: what applies the deferred trigger

**Method.** Temporary timing prints in `FleetSequencer` (not committed): one
line per drain request and per forward on every follower, `ok` or `failed`
with its duration. Four probed runs on 2026-10-08 (03:59-04:13), each pod's
lines read from its kept log; then the IT re-run after each harness fix.

**What the probe showed.**

| Run | Phase | During the cut, per pod | After the heal, pod1 |
|---|---|---|---|
| 04:00 | M=10 | 1 forward + 9 drains failed, 1,006-1,027 ms | drain ok 169 ms, forward ok 28 ms |
| 04:00 | M=1,000 | 1 forward + 249 drains failed per pod (4 pods), 1,004-1,222 ms | its drain failed, ~1.1-1.2 s: deferred |
| 04:05 | M=10 | 1 forward + 9 drains failed, 1,033-1,123 ms | drain ok 775 ms, forward ok 104 ms |
| 04:06 | M=10 | 1 forward + 9 drains failed, 1,006-1,023 ms | drain ok 140 ms, forward ok 25 ms |
| 04:06 | M=1,000 | 1 forward + 249 drains failed per pod, 1,028-1,205 ms | its drain failed: deferred |
| 04:13 | M=10 | 1 forward + 9 drains failed, 1,034-1,272 ms | its drain failed: deferred |

- **Every partitioned flush asks for a drain and times out at the 1 s peer
  timeout.** The peer client keeps no connection alive, so each is a new
  connection, and `ChaosProxy` accepted and held each one.
- **At the heal it delivered all of them.** That is up to 1,000 drains of
  requests long abandoned, reaching the leader together. Drains are
  serialised, so the trigger's own drain queued behind them, outlasted 1 s,
  and the trigger deferred.
- **What then applied its intent was one of those stale drains,** landing after
  the trigger's intent was written: luck, not design. That is the answer to
  M13.3's OBSERVED-NOT, and why the post-heal drain looked slow.

**After the harness fix** (`ChaosProxy.dropAbandonedAtHeal`, used by this IT
only; and one keep-alive-free client per timeout for the partitioned writes),
five runs, all red, now plainly (then three more, below):

- M=10: four runs forwarded the trigger and drained, three in 189-202 ms and
  one in 881 ms, over the M=10 bound (the trigger's 202 alone took 853 ms);
  one run's trigger deferred (1,510 ms) and its intent remained (`remaining=1`).
- M=1,000: the trigger deferred at 1,033 ms, the leader's drain completed
  without it, and its intent remained (`remaining=1`).
- Two runs failed earlier on Helidon's `Exception in socket monitor thread`
  for a partitioned write, before the keep-alive change. Three runs after it
  acked every partitioned write and all failed only at `remaining` at
  M=1,000 (the last: M=10 drained in 319 ms; M=1,000 deferred at 1,112 ms,
  `remaining=1` at 7,537 ms). Too few runs to call the error closed.

So the slow tail is not drain throughput. **A pod asks for a drain only on its
next flush.** When the one it asks at the heal times out, its trigger and every
intent behind it wait for a write that, in this IT, never comes. That is
M13.78. The bound is not moved.

**Not separated, and why that no longer decides the outcome.** Container age
and state, memory, and the drain's apply and delete phases were not measured
apart. They set how long a 1,000-intent drain takes, and whether it beats the
1 s timeout. But any drain longer than the forward timeout reproduces the
stranded trigger, so they decide how often the gap shows rather than whether
it exists. Re-measure them against M13.78's bound if it is still missed.
