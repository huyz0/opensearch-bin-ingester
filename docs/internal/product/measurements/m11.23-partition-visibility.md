# M11.23 partition visibility on M9's rig

Status: measured on 2026-09-28, on M9's rig. Root-caused to the RustFS test
fixture, not to the drain path. `PartitionVisibilityIT`'s 2,500 ms bound is
unchanged.

## Rig

The rig `m9.12-partition-visibility.md` records, re-read on this run:

- Intel Core i5-13600KF, 14 physical / 20 logical cores
- Windows 11 Pro 64-bit build 26200; Temurin OpenJDK 25.0.4.1+1-LTS
- Docker Desktop 29.8.0 (WSL2 kernel 6.18.33.2), 20 CPUs, 31.3 GiB
- RustFS `rustfs/rustfs@sha256:8cc98017...` (1.0.0), `mem_limit: 256m` as committed

M11.19's 2,830-2,889 ms were measured on a different machine, a 4-core Linux
container.

## What the IT's clock covers

The bound's clock starts before `heal()` and the post-heal trigger write. This
task adds separate timings, printed as `M11.23 inbox=M writes= trigger202=
drainEnd=`:

- `writes`: the partitioned write phase, outside the bound.
- `trigger202`: heal to the trigger write's `202`, inside the bound.
- `drainEnd`: heal to an empty inbox. This is the number the bound checks.

## RustFS memory (`docker stats`, readings at each run's start and end)

- The long-lived 256m container (up since 2026-09-25), runs 1-4 in sequence:
  203.2 -> 227.8, 226.2 -> 241.4, 251.3 -> 240.3, 237 -> 254 MiB. It was never
  OOM-flagged while observed. During the bisection it went down twice
  (`0B / 0B`) and was recreated by the next `docker compose up`; the replaced
  container's OOM flag was not recoverable.
- A fresh 256m container: 239.3 MiB after its first run (run 5, the slowest
  drain measured, 3,666 ms), 236.2 after the second; F1-F2 on another fresh
  container: 241.4, then 230.8, then 246.4.
- A fresh 512m container: 332 -> 389 -> 452 MiB over three consecutive runs.

**One run of this IT takes RustFS to ~94% of a 256m limit, fresh or not.** It
does not grow further there: the readings stay between 230 and 254 MiB. Steady
growth across runs is seen only at 512m, where there is room to grow. So the
container's age is NOT the variable: a fresh container's first run was the
worst result. The limit is.

## Conclusion

**Criterion 1's outcome (c), with the cause named.** At 256m the committed code
drains in 1,635-3,666 ms (7 measured drains, 2 over the bound) and lost the
store twice, whether the container is fresh or long-lived. With 512m it drained
in 1,488-1,780 ms, 3 of 3 green and below M9's 2,209 ms. It is not reliably
green as committed until the fixture's memory limit is settled, which is
M12.24.

- **No regression on the drain path.**
  - The strongest evidence is the 512m runs: the same committed code, below
    M9's own 2,209 ms.
  - `GoverningBinStore.get` and `getRange` are pass-throughs, and
    `HealthTrackingBinStore` adds one map entry per request.
  - Variant A (the drain's reads off the governed stack) passed three times,
    within the spread the committed stack also shows (1,635-2,067 ms).
  - Variant B (without `CommitChargingBinStore`) is inconclusive: one valid
    run (4,197 ms, at 243 of 256 MiB), and two that lost the store.
- **The cause is the fixture's memory limit, plus a test defect.**
- **The trigger write takes ~1.03 s** of the 2,500 ms in almost every run
  (70 ms once). Part of the bound's budget goes to the trigger, not the drain.
  It was not investigated further here.
- **Test defect found and fixed.** The writers were joined with sequential
  120 s waits, but each partitioned write waits out the 1 s TTL-bound forward,
  so a writer takes ~255 s. A writer still running when its join returned
  surfaced as "expected 1000 but was 999", with no failure recorded. The writers
  now share one 480 s deadline (the old joins' worst case), and a writer still
  running at the deadline fails, naming its follower.

`mem_limit` is not changed here. A fresh container per run would not fix it
(run 5); the limit itself is M12.24's decision, reasoned against build.md's
WSL2 rule, together with the budget that reads `mem_limit` (in this tree only
the retired `scripts/test_budget.py`; no Gradle gate reads it).
