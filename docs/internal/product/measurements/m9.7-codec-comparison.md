# M9.7 codec and block-size comparison

Status: measured on 2026-09-22. This is the B3 measurement for M2, not a
wire-format change. The production segment writer does not yet expose codec
selection, so the macro run validates the assembled RustFS path while the codec
choice is measured at the B3 seam.

## Method

`CompressionBenchmark` ran all 15 combinations of zstd levels 1, 3 and 6,
lz4, and none at 64 KiB, 256 KiB and 1 MiB. The fixture is deterministic,
varied JSON-like data with 200 B, 1 KiB and 10 KiB document shapes. Each point
used two forks, five one-second warmups, five one-second measurements, and
`-prof gc` on the pinned Temurin JDK 25 rig from M9.6.

MiB/s is per benchmark thread/core. Ratio is uncompressed block bytes divided
by the measured compressed bytes per operation. B/op is JMH's
`gc.alloc.rate.norm`; it remains in the table so speed alone cannot select a
codec.

## Decision

The documented default candidate remains zstd-3 at 256 KiB: it retains nearly
the zstd-1 ratio while avoiding zstd-6's large throughput penalty. This is a
measurement conclusion only. No persisted segment bytes, codec flags, reader,
writer, or production default changed in M9.7; a future production default
change must travel through `wire-format-change` and an ADR.

The RustFS T3 anchor passed with:

```text
:server:integrationTest --tests io.github.huyz0.os.biningester.server.chaos.MacroHarnessIT
BUILD SUCCESSFUL
```

That macro result proves the assembled RustFS path still runs with the current
writer configuration. It is deliberately not labelled as 15 end-to-end codec
runs because codec selection is not yet a production setting.

Rig: Windows 11 Pro 64-bit build 26200; Temurin OpenJDK 25.0.4.1+1-LTS;
Intel Core i5-13600KF, 14 physical / 20 logical cores. RustFS was the pinned
single-node fixture qualified by M9.22.
