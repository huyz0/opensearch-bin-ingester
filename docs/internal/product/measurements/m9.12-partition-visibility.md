# M9.12 partition visibility

Status: measured on this rig on 2026-09-22. These are measured RustFS rig
observations and a modelled lower-bound proxy for production NFR-7: RustFS is a
test fixture, not a supported backend, and an S3 PUT tail was not run.

## Method

`PartitionVisibilityIT` started a leaseholder and up to four follower
processes, cut the peer socket through the real Windows child-process HTTP
path, and issued one-record writes until the inbox held M durable intents. The
test healed the socket, issued one post-heal write to request the drain, then
audited the RustFS chain for every record that had received a 202 on an intent.

The fixed adaptive-interval ceiling was 250 ms. The acceptance bound is
`max(2, ceil(M/100))` interval ceilings. Inbox intents are committed in one
`commitAll` batch per pod; their independent bodies are read concurrently, but
the request count remains one LIST per 1,000 intents and one GET per intent.
The commit HTTP service uses a fair drain barrier so late healed sockets cannot
advance a pod's dedupe mark while its intents are being reconciled.

| Inbox M | Acked records | Drain latency | Bound | Chain audit |
|---:|---:|---:|---:|---|
| 10 | 10 | 182 ms | 500 ms | all visible, no duplicate offsets |
| 1,000 | 1,000 | 2,209 ms | 2,500 ms | all visible, no duplicate offsets |

Both points passed. The production interpretation is modelled as a lower
bound: the RustFS loopback fixture does not include an S3 PUT tail, so these
numbers do not complete a production-cloud NFR-7 claim.
