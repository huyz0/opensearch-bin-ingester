# M9.5 JFR profile of the RustFS macro harness

Status: measured on 2026-09-21. This is L5 profiling evidence for M9
criterion 10; it is not a latency or throughput gate.

## Rig and run

| Item | Value |
|---|---|
| OS | Windows 11 Pro 64-bit, build 26200 |
| JDK | Temurin OpenJDK 25.0.4.1+1 LTS |
| CPU | 13th Gen Intel Core i5-13600KF, 14 physical cores / 20 logical processors |
| Memory | 68,543,528,960 bytes reported by Windows |
| Store | RustFS `rustfs/rustfs@sha256:8cc9801755448b71a786705ce76692c77e14936cccd87cf2fc31842e58f4d1ff` |
| Workload | `MacroHarnessIT` with the seeded workload, temporarily expanded to 400 documents for profiling only |
| JVMs | Three assembled node processes from the macro harness; the committed acceptance test remains 12 documents |

The two runs used the same checkout, JDK, RustFS digest, workload seed and
JFR `profile` settings. `jcmd` started one recording per node and dumped it
periodically while the node was alive; this is required because the harness
force-terminates child JVMs after the assertion. Each run produced three valid
recordings of approximately 31--34 seconds, and the macro integration test
passed.

The raw recordings are local working artifacts under
`build/m9.5-profile/run9` and `build/m9.5-profile/run10`; this committed note
is the durable evidence. No profiling-only workload change remains in the
tree.

## Reproducible hotspots

The profile's aggregate CPU-time view had no events for this short run, so the candidates below are explicitly allocation-pressure hotspots from
JFR's `allocation-by-site` view. The percentages are the largest observed
allocation-pressure share for that method in one node recording in each run;
they are not CPU percentages.

| Candidate hotspot | Run 9 | Run 10 | Why it is carried to M9.6 |
|---|---:|---:|---|
| `software.amazon.awssdk.http.auth.aws.internal.signer.chunkedencoding.ChunkedEncodedInputStream.getChunk(InputStream)` | 42.11% | 41.28% | Reproduces on the object-store write path; measure request-body/chunk allocation before considering an alternative. |
| `java.util.concurrent.ConcurrentHashMap.initTable()` | 36.47% | 37.68% | Reproduces in the assembled-node runtime; measure initialization and contention-sensitive map setup with realistic stream cardinality. |
| `java.util.HashMap.resize()` | 13.25% | 13.86% | Reproduces as map growth pressure; measure the relevant routing/metadata path before changing capacities. |

JFR-internal setup and class-loading sites also appear because the assembled
processes are short-lived. They were not selected as application candidates.
The next task, M9.6, must validate these candidates with JMH and `-prof gc`
before any optimization is proposed.
