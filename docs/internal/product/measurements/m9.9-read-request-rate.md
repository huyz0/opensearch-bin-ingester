# M9.9 read request rate

Status: measured on this rig on 2026-09-22. These are measured RustFS rig
observations, not a production-S3 dollar estimate.

## Method

`ReadRequestRateIT` used one RustFS object and a `CountingBinStore` around an
independent observer client. A serving ingester node had one
`SegmentProxy` and one byte-bounded `SegmentCache`. Each case published the
same segment three times: the remote proxy arm, the held-bytes inline arm, and
a late consumer replay. The replay is the falsifier for a disabled cache.
Consumer nodes were registered against the
same serving node, and the three-node point distributed them across three
independent serving-node caches. Each point published the remote proxy arm,
the held-bytes inline arm, and then a late-consumer replay.

The 16- and 1,600-shard points used one segment carrying one run per shard.
The run list was split among consumer subscribers, so the assertion observes
real subscriber grouping rather than calling the proxy once per run.

| Point | Consumer nodes | Serving nodes | Shards | GET delta |
|---|---:|---:|---:|---:|
| baseline | 1 | 1 | 16 | 1 |
| consumer fan-out | 9 | 1 | 16 | 1 |
| serving-node fan-out | 9 | 3 | 16 | 3 |
| shard fan-out | 9 | 1 | 1,600 | 1 |

The inline delivery in every point added zero GETs. The consumer-node change
from one to nine is 0%; the shard change from 16 to 1,600 is 0%; and three
serving nodes cost one cold GET each. The 1,600-shard point is therefore below
the 1.2x NFR-4 bound, while the observed serving-node term is exactly one GET
per serving node. The same test also asserts that 1,600 real
`NodeSubscriptions` shard registrations use one merged subscription, not one
transport subscription per shard. The proxy/cache arm is the one a disabled
cache makes red.
