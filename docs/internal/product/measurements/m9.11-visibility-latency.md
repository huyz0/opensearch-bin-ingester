# M9.11 visibility latency

Status: measured on this rig on 2026-09-22. These are measured RustFS rig
observations and a modelled lower-bound proxy for production NFR-7: RustFS is
a test fixture, not a supported backend, and an S3 PUT tail was not run.

## Method

`VisibilityLatencyIT` ran 10,000 records at each fixed adaptive-interval
ceiling, in 1,000-record writes. A consumer was already polling while the
producer wrote, so the timestamp is taken immediately after each real 202
response and the end is the matching record's delivery through
`ConsumerClient`. HdrHistogram records the distribution. The 64 MiB segment
limit keeps these points interval-triggered rather than size-triggered.

| Ceiling | Records | p50 | p99 | Max | 3× ceiling |
|---|---:|---:|---:|---:|---:|
| 250 ms | 10,000 | 0.942 ms | 11.395 ms | 11.428 ms | 750 ms |
| 1 s | 10,000 | 0.864 ms | 13.681 ms | 13.705 ms | 3 s |
| 5 s | 10,000 | 0.892 ms | 3.396 ms | 3.426 ms | 15 s |

All three p99 values are below the ADR-0063 ceiling divisor's bound on this
rig. The production interpretation is modelled as a lower bound: RustFS
loopback does not include an S3 PUT tail, so these numbers do not complete a
production-cloud NFR-7 claim.

## Searchable point

`SearchableIT` in `clusterTest` used the 1 s ceiling and 1,000 documents. The
documents were returned by an OpenSearch match-all search with p99 **537.919
ms**, below the 3 s bound. Because this T4 seam has no HTTP front door, its
timestamp is immediately before the in-process durable handoff, conservatively
including that handoff as well as consumer delivery, the ingestion engine and
Lucene refresh/search. The T3 test above is the exact producer-202 endpoint;
this T4 point is the searchable-tail observation, not a second HTTP-endpoint
claim.
